# OpenCode v1.14.48 Message ID Wraparound Causes Resumed Sessions to Idle Without Reply

## Status

- Target: OpenCode `v1.14.48`
- Severity: P0 for long-lived/resumed sessions that cross the MessageID wrap boundary
- Fix strategy: backport the completed-turn parent linkage check from upstream PR #40990
- Upstream reference: `anomalyco/opencode#40990`, merge commit `db581e47a3a6f4900a6289ad7fddec60fec44e1c`

## Problem statement

A session created before a MessageID timestamp wrap can become permanently unusable when it is resumed after the wrap. A new user message is persisted, the session briefly becomes busy, then the prompt loop exits at step 0 without resolving tools or calling the model. The caller observes a completed/idle turn with no assistant output.

The failure is deterministic for the affected session shape: an older completed assistant message has an ID that sorts lexicographically after a newer user message because the time component embedded in the ID has wrapped.

## Observed behavior

For an affected resumed session:

1. A new user message is accepted and stored.
2. The prompt loop starts with `step=0`.
3. No tool resolution happens.
4. No LLM stream is started.
5. The loop logs `exiting loop` immediately.
6. The session transitions back to idle with no new assistant message.

The user-visible symptom is a near-instant empty completion / idle response.

## Root cause

OpenCode v1.14.48 selects the latest user and assistant from the time-ordered message stream, but decides whether the latest user has already been answered using the following condition in `packages/opencode/src/session/prompt.ts`:

```ts
lastUser.id < lastAssistant.id
```

This assumes lexicographic MessageID order is globally monotonic with creation time.

Message IDs encode a timestamp-derived value into 6 bytes. After the effective timestamp field wraps, a newer message can have a lexicographically smaller ID than an older message. A representative affected sequence is:

```text
old user       msg_ff...   time.created = T1
old assistant  msg_ff...   time.created = T2, finish=stop, parentID=old user
new user       msg_00...   time.created = T3 > T2
```

The prompt loop correctly identifies the `msg_00...` message as the latest user by time/order in the message stream, but the completion check evaluates:

```text
msg_00... < msg_ff...  => true
```

and incorrectly concludes that the new user message has already been answered.

## Correct behavior

A completed assistant response proves that the current latest user has been answered only when that assistant explicitly points to that user via `parentID`.

The completion check must therefore use parent linkage rather than relative ID ordering:

```ts
lastAssistant.parentID === lastUser.id
```

This is the same semantic fix used upstream in PR #40990.

## Scope

### In scope

- OpenCode `v1.14.48` session prompt loop.
- Resumed sessions containing non-monotonic MessageIDs.
- MessageID wraparound where a newer user ID sorts before an older completed assistant ID.
- Regression coverage proving that a new user message is processed even when its ID is lexicographically smaller than the previous assistant ID.

### Out of scope

- Changing the MessageID binary/string format.
- Expanding the 6-byte timestamp representation.
- Migrating or rewriting existing persisted IDs.
- Backporting the later `MessageV2.latest()` refactor from newer OpenCode versions.
- Changing provider/model retry or streaming behavior.

## Proposed change

In `packages/opencode/src/session/prompt.ts`, replace the ID-order completion predicate:

```ts
lastUser.id < lastAssistant.id
```

with the explicit response-parent predicate:

```ts
lastAssistant.parentID === lastUser.id
```

Keep the existing guards for completed finish reasons and tool calls unchanged.

## Compatibility

The change preserves the intended semantics for normal sessions:

- A completed assistant whose `parentID` is the latest user still terminates the loop.
- `tool-calls` continues to keep the loop running.
- Assistant messages containing non-provider-executed tool calls continue to keep the loop running.
- A newly appended user message always causes another model turn unless a completed assistant explicitly belongs to that user.

No persisted-data migration is required.

## Regression test

Construct a session with deliberately non-monotonic IDs:

```text
oldUser.id       = msg_ff_user
oldAssistant.id  = msg_ff_assistant
oldAssistant.parentID = oldUser.id
oldAssistant.finish   = stop
newUser.id       = msg_00_user
newUser.time.created > oldAssistant.time.created
```

Queue one LLM response and call `SessionPrompt.loop()`.

### Expected assertions

- The LLM is called exactly once.
- The returned assistant is not the old assistant.
- The returned assistant has `parentID === newUser.id`.
- The response contains the queued model output.

The test must fail on unmodified v1.14.48 because the loop exits before the LLM call.

## Acceptance criteria

1. An affected cross-wrap resumed session no longer exits at step 0 solely because the new user ID sorts before the old assistant ID.
2. A completed assistant still terminates the loop when `assistant.parentID === latestUser.id`.
3. Existing tool-call continuation semantics are unchanged.
4. The non-monotonic-ID regression test passes.
5. The patch is limited to the v1.14.48 backport and does not pull unrelated later OpenCode changes.

## Operational mitigation before deployment

For already affected production sessions, forcing creation of a new native OpenCode session remains a valid temporary mitigation. The code fix prevents the bad completion decision when such sessions are resumed after deployment.
